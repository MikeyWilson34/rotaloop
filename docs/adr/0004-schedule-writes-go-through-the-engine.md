# Schedule writes go through the engine on the server

Every change to a Group's scheduling state (Members, Responsibilities, Rotations, Event Series, Events, Time Off, Assignments, Make-up Turns, settings) goes through one Supabase Edge Function, `group-command`. It authenticates the caller, resolves their Member id, loads the Group's rows into a `GroupState`, runs the rotation engine's `applyCommand` with the server's clock, and persists the result plus its schedule-history entries in one transaction by calling `apply_group_command_result`. That call is guarded by an optimistic lock on `groups.state_version`: on a conflict the function reloads and retries a few times, then returns `conflict`. This lock is what makes "first accept wins" on a Coverage Request race-safe, because the losing retry sees the Cover and the engine rejects it with `alreadyCovered`. Creating a Group, joining by invite link and claiming a Placeholder are also `group-command` actions, so the engine runs for them too. Clients never write scheduling tables. They read them through RLS: active Members can read everything in their Groups, which includes history and workload, since everyone may see those. Group health is derived on the client (originally shown only to Admins; see 0006). Clients write only their own profile and push tokens, plus a few RPCs (reset invite link, claim link, rename Group; Admin-only until 0006) that don't touch engine state. Engine ids are unique per Group only, so engine-owned tables use `(group_id, id)` keys, and a `position` column keeps each `GroupState` array's order so that rows and state round-trip exactly. The function imports the engine and the row mapping (`src/engine`, `src/db`) as generated copies in `supabase/functions/_shared/`. `npm run functions:sync` writes them and adds the `.ts` extensions Deno needs. `npm run functions:deploy` runs the sync and then deploys.

## Consequences

- One code path computes the schedule, so the server can't drift from the engine's tests. Every write costs a full load of the Group's state and an upsert of the full state; unchanged rows are skipped, so Realtime sees only real changes. That cost is fine at volunteer-team scale.
- The engine enforces every permission rule (own Time Off, acting for a Stand-in; originally also Admin-only commands and the last-Admin guard), so the rules live in one place. **Superseded in part by [0006](0006-members-only.md):** there are no Admin-only commands for now; every active Member may run them. `src/db/handleGroupCommand.ts` only authenticates the caller and resolves their active Member id (ticket 13).

## Attendance-style Events (later)

_Built differently as Headcount jobs (simplify ticket 09, migration `20261124000000_headcount_jobs.sql`): a `responsibilities.kind` of `headcount` and a `headcount_answers` table, written through `group-command` like everything else. The plan below is kept for history._

Attendance-style Events will add an `events.kind` column (`'rotation'` by default, or `'attendance'`) and an `event_responses` table keyed by `(group_id, event_id, member_id)`, holding a response (in / out) and when it was given. "No reply yet" is simply a missing row. Answering is per Member and doesn't affect Rotations, so responses can be written by their owner through RLS or a small RPC rather than through the engine. Attendance Events need no Responsibilities, and the engine already skips Events whose Responsibility list is empty. No existing table changes shape.
